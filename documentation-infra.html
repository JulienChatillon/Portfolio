Contexte et objectifs

Avec l'évolution constante de mon laboratoire (PVE2) et de mon environnement de production (PVE1), la quantité de services déployés a rapidement augmenté : routage pfSense, annuaire Active Directory, tunnels WireGuard, supervision, etc. Il devenait indispensable de structurer mes prises de notes initialement réalisées sur Notion. Ce projet est né de la volonté de créer une véritable base de connaissances centralisée, capable de tracer l'architecture de mon réseau et de détailler mes procédures de déploiement. Pour partager ce travail sans compromettre la sécurité de mon infrastructure, j'ai mis au point un système de publication qui filtre les données sensibles d'un dépôt privé vers un dépôt GitHub public.

Objectifs

  1. 1

    Centraliser et pérenniser la documentation technique de l'ensemble de l'infrastructure (topologies réseaux, stratégies de sauvegarde, PRA).

  2. 2

    Mettre en place un flux de publication sécurisé (dépôt privé vers dépôt public) garantissant l'anonymisation des adresses IP critiques et des informations sensibles.

  3. 3

    Rédiger des procédures d'exploitation et de configuration détaillées et reproductibles (création de cluster, certificats PKI, règles de pare-feu).

  4. 4

    Partager mon environnement d'apprentissage et mes maquettes avec d'autres étudiants ou professionnels via une plateforme accessible (GitHub).

Mise en œuvre

1

Prendre des notes sur Notion

Je note chaque manipulation dans mes cours personnels, un module par sujet : Proxmox, VPN WireGuard, Windows Server, GLPI, reverse proxy, supervision. Ces notes servent aussi à des camarades, qui y accèdent par un lien de partage.

2

Structurer la documentation en Markdown

Je reprends ces notes dans un dépôt GitHub privé : un dossier par thème (architecture, production, laboratoire, supervision) et un README qui sert de sommaire. Chaque document décrit une brique de l’infrastructure et sa procédure.

3

Repérer ce qui ne doit pas être publié

Les adresses IP et les noms de zones réseau sont remplacés par des marqueurs. Pour un passage entier qui doit rester privé, je l’entoure de deux balises de commentaire : le script le supprimera.

4

Écrire le script de nettoyage

Un script Python copie le dossier de documentation et le README dans un dossier de sortie. Il supprime les blocs entre les balises privées, puis remplace chaque valeur listée dans un fichier de correspondance par son marqueur. Ce fichier reste dans le dépôt privé.

5

Automatiser la publication

Une action GitHub se lance à chaque enregistrement sur la branche principale : récupération du dépôt privé, installation de Python, exécution du script, puis envoi du résultat vers le dépôt public. Le jeton d’accès est stocké dans les secrets du dépôt, pas dans le code.

6

Vérifier

Je contrôle dans l’onglet Actions que les exécutions réussissent, puis que le dépôt public ne contient que la documentation nettoyée, avec les adresses remplacées par des marqueurs.

7

Relier la documentation à mon portfolio

Le dépôt public est référencé depuis mon portfolio et depuis mon profil GitHub, ce qui en fait une vitrine de ma méthode de travail.

Difficultés rencontrées

Problème

Je voulais partager mes projets et ma documentation sans dévoiler les informations sensibles de mon infrastructure, mais sans rédiger et entretenir deux documentations.

Solution

J’écris une seule documentation, dans le dépôt privé, avec les vraies valeurs. Le filtre automatique produit la version publique : blocs privés supprimés, valeurs remplacées par des marqueurs.

Bilan

Ce projet m’a obligé à expliquer clairement ce que j’avais mis en place, ce qui a consolidé mes acquis. Le filtre automatique m’a sensibilisé à la sécurité de l’information : documenter sans exposer l’infrastructure. Je dispose aujourd’hui d’un support fiable pour reconstruire ou dépanner mon laboratoire, partagé avec des camarades, et d’une vitrine de ma méthode de travail.
